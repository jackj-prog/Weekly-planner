# Week OS — audit, September 2026 (against v4.35.0)

Findings for Codex, ranked by impact. Every claim below was verified against
the running app or the source at the line given — none of it is inferred from
reading alone. Screenshots were taken with `tools/shoot.js` at 390×844.

The design work in v4.29–v4.34 fixed what it set out to fix: typography now
honours §3, the EF chart is honest, the week view reflects effort back, the
rest-day state is genuinely good. Nothing below walks any of that back. The
findings split into two groups — **the run log is lying about distance**, which
is a data-integrity problem the recent progress features made more visible, and
**getting a run into the app is a slog**, which is the user's own words and the
most valuable thing left to build.

---

## 1 · The distance a run actually covered cannot be recorded — HIGH

`CLAUDE.md` §2 defines the store as `runlog-ISO = {sec, hr, km?}`, and
`runLogHistory()` (`js/app.js:447`) reads `e.km || day.run.run.km`. The
optional override is read everywhere and **written nowhere**: there are zero
occurrences of a `km` stepper in the log form (`js/app.js:582–600`). The six
rows are pace, avg HR, first-half pace, second-half HR, feels-like, gels.

So the app records the distance it *prescribed*, never the distance that was
run.

Concrete case from this week: Thursday 10 Sep prescribed 5 km. The user ran
6.9 km. There is no way to enter that.

**What it corrupts.** Not EF — that is computed from pace, so the km term
cancels and the number stays correct. But every cumulative distance figure is
wrong: the "km logged" stat on the week view, the weekly totals, and the
shortfall arithmetic in `longRunGuard()`. The v4.34 progress features made this
worse by putting those numbers on screen and inviting trust in them. "42 km
logged" currently means "42 km were prescribed on days you logged something."

**Fix.** Add a km row to the log form, defaulting to the prescribed distance so
the common case stays one glance. Store it only when it differs. See §3 — the
paste importer should fill it automatically.

---

## 2 · "Behind" conflates *not logged* with *not done* — HIGH

`longRunGuard()` (`js/app.js:~600`) computes `ranSoFar` purely from
`getRunLogEntry(d)`. A run that was ticked done but never logged counts as
zero kilometres.

The result, verified on screen: on the morning of the week 11 long run, with no
log entries, the hero reads **"0 of 22 km this week so far — 22 km behind."**
The user may have run every one of those kilometres.

This is not a cosmetic mismatch. It is the app telling a disciplined athlete he
is 22 km down immediately before the longest run of his block, on no evidence.
The note it introduces exists to stop exactly that thought.

**Fix.** Count a ticked-done run at its prescribed distance when no log exists.
Reserve the word "behind" for runs that were neither ticked nor logged, and say
"not logged yet" for the rest. Ticking and logging are different acts and the
copy should never merge them.

---

## 3 · Getting a run in is a slog — HIGHEST VALUE

The user's words: *"there must be a seamless way to implement run data which
isn't a tedious slog."* He is right, and the numbers are unflattering.

Steppers move in fixed increments (`data/plan.js:471–486`): pace 5 s/km, HR
2 bpm, temp 1°. Logging Thursday's run against its own estimate would cost
**7 taps on pace alone**, before HR, temperature, and — for a long run — two
more rows for decoupling. A long run is 20–30 taps.

Worse, `hrStep: 2` makes **odd heart rates unrepresentable**. Thursday's
average was 151 bpm. From a centre of 152 the reachable values are 150 and 152.
151 cannot be entered at all.

### 3a · Paste-to-parse — build this first

The user already produces structured run text; he pastes it into chat after
every run. Give the app a textarea that accepts it.

```
distance=6899.8m  moving=2413s (40:13)  avg_pace=5:50/km  HR_avg=150.68 ...
```

Tolerant regexes over distance, moving time, average HR, temperature and pace,
order-independent, accepting both `6899.8m` and `6.90 km`, `40:13` and `2413s`.

**Do not replace the steppers — seed them.** Paste, show a parse preview
("Found: 6.90 km · 40:13 · 151 bpm · no temperature"), fill the existing rows,
let him correct anything before saving. Zero taps in the common case, and the
correction path is the UI that already exists. This also solves §1 for free,
because a parsed distance is a real distance.

Pure string handling. No dependency, no network, works offline.

### 3b · GPX / TCX import — the version worth showing off

`<input type="file" accept=".gpx,.tcx">` works in iOS Safari, and `DOMParser`
is built in, so parsing Strava's export needs no library and no build step.

A full stream gives what no amount of stepper-tapping can:

- exact distance and moving time, with no override needed
- true time-weighted average HR
- **real aerobic decoupling** from the actual halves, retiring the two
  approximation rows the form currently carries
- **real zone distribution** — see §4, which this fixes at the root
- negative-split detection, which matters directly for race pacing

### 3c · Ruled out — do not spend time here

- **Strava API.** OAuth token exchange requires a client secret. There is no
  backend and there must not be one. Dead end.
- **Web Share Target.** Not supported by iOS Safari. Dead end.
- **Apple Health / HealthKit.** Unreachable from a web app. Dead end.

## 4 · Intensity distribution buckets a whole run by its average HR — MEDIUM

`js/app.js:1716–1720` calls `DB.zoneOf(e.hr, …)` once per run and adds the
entire duration to that single zone.

Thursday's run averaged 150.7 bpm — Z2 — but its middle three kilometres ran
154–157, which is Z3. All 2,413 seconds are currently filed as Z2.

The bar is described in its own comment as *"the only real audit of rule 1"*.
It systematically understates time spent above Z2, which is precisely the
failure rule 1 exists to catch. A drifting run and a genuinely easy run with
the same average are indistinguishable to it.

**Fix.** Honest short-term option: label it "by average HR" so it does not
claim more than it knows. Real fix arrives with §3b — a HR stream buckets
second by second.

---

## 5 · The long-run guard renders outside the disclosure — MEDIUM

`js/app.js:667` renders `longRunGuard()` immediately after `h-detail`, never
inside a `<details>`. On the long-run morning it is seven lines of body copy in
the hero, and it pushes the log form below the fold.

The collapse mechanism built in v4.31 sits directly above it, unused. Show the
headline sentence; put the reasoning behind the same disclosure everything else
uses.

---

## 6 · Pace left the run hero — MEDIUM (spec regression)

`h-meta` (`js/app.js:664`) carries SHOE and WINDOW. CLAUDE.md §4.2 requires
*"distance, session, shoe, pace visible without scrolling."* Pace is now behind
the Details tap, with the zone chip in its slot.

The zone is the right call for HR-led prescription and should stay. But the
easy-pace band for the week (6:10–6:35 in weeks 7–13) is a number you leave the
house with, and §4.2 is explicit. Fit both, or amend §4.2 deliberately — do not
leave the spec and the app disagreeing.

---

## 7 · An unplanned run cannot be recorded at all — MEDIUM

`logHTML` is built inside the run hero, which only renders when the day carries
a prescribed run. Monday is a zero day from week 17; the holiday template rests
Mondays; race week moves runs around. Any run on a day the plan did not
schedule has nowhere to go, and so never reaches EF, the zone bar, or any
progress figure.

**Fix.** An "add a run" affordance on rest days, writing the same `runlog-ISO`
shape with an explicit km. Pairs naturally with §3a.

---

## 8 · Smaller things

- **`hrStep: 2`** (`data/plan.js:472`) — halve it to 1. Two taps saved is worth
  less than being able to enter the number you actually saw.
- **Now/Next vertical alignment.** When a block title wraps to three lines the
  time column centres against it and reads misaligned. Top-align it.
- **"Build begins"** sits beside the phase chips as orphaned grey text with no
  clear relationship to them.

# Second pass (v4.36 → v4.37)

A deeper scan of the parts the first pass did not reach: date arithmetic,
offline integrity, backup coverage, test coverage and colour contrast. Four
defects, all fixed in v4.37 rather than logged, because each was a hole in a
safety net rather than a design decision. What was checked and found sound is
listed too — an audit that only reports problems tells you nothing about
where it looked.

## 9 · `--t3` was below WCAG AA, and it sets the smallest text — FIXED

The v4.36 repaint shipped `--t3` at **4.23:1** against paper. AA needs 4.5,
and `--t3` sets the timeline *times* at 11px — the smallest text in the app,
where contrast matters most, read outdoors and at 06:00. Now `#656c5d`, 4.83:1
on paper and 5.36:1 on surface.

Nothing caught it because nothing was looking. §11 fixes that permanently.

## 10 · `--accent` was doing two incompatible jobs — FIXED

Found by the new guard on its first run, which is the best argument for it.

In dark mode `--accent` must be **light** to work as text on a near-black
ground (the NOW label, the countdown), and **dark** to sit behind white text
as a fill (the race hero, primary CTAs, hot chips). Those requirements point
in opposite directions and one token cannot satisfy both: after lifting it for
legibility as text, white-on-accent fell to **3.20:1** — on the race-day hero,
in the dark, which is precisely the screen and the lighting this app exists
for.

Split into `--accent` (text, lifts in dark) and `--accent-fill` (stays deep in
both themes, so white always reads on it). Decorative fills with no text on
them — progress bars, timeline dots — correctly keep `--accent`.

## 11 · Nothing was checking contrast at all — FIXED

`tests/build.test.js` now parses the real tokens out of `css/style.css` — both
the light `:root` and the dark block — and fails if any text-on-ground pair
drops below AA. It reads the stylesheet rather than a copy of the values, so
it cannot drift.

No future repaint, by anyone, can quietly make the app unreadable in the
conditions it is actually used in. The suite is now **15,941 checks**.

## 12 · The privacy allowlist had grown a blind spot — FIXED

The guard that stops real resting/max HR reaching this public repo scanned
`plan.js`, `day-builder.js`, `app.js` and itself. It did **not** scan
`js/ef-chart.js` or `js/run-progress.js`, both added in v4.29–4.34 and both
handling run data. A guard with a gap the codebase has since grown past is
worse than no guard, because it is trusted. Both files are now in the list.

## Checked and sound — no action needed

- **DST.** `addDays()` uses `setDate`, which is DST-safe. `daysBetween()`
  divides by `DAY_MS` and rounds; across the block's single autumn transition
  the drift is ~1 hour against a 24-hour divisor, so the rounding absorbs it.
  Week numbers and day indices hold across 25 Oct 2026.
- **Offline integrity.** `sw.js` `ASSETS` includes both new modules. A missing
  entry there would break the app offline and then cache the breakage; it did
  not happen.
- **Backup coverage.** Every key the app writes — `done-`, `ovr-`, `movein-`,
  `runlog-`, `wt-`, `recal`, `hr` — is matched by `STORE_KEY`. Only
  `backup-at` and `schema-v` are excluded, correctly, as metadata. Nothing a
  user could lose is outside the backup.
- **New-module test coverage.** `ef-chart.js` and `run-progress.js` are UMD
  and carry dedicated suites (`tests/ef-chart.test.js`,
  `tests/run-progress.test.js`), so a syntax error fails at require time. They
  do not need adding to the `node --check` list.

## What not to change

The v4.29–4.34 work is sound and this audit assumes it stays. In particular:
the type roles, the EF chart's fixed reference scale and its "too few runs to
call a trend" honesty, the rest-day pause state, the week distance profile, and
the phase progress strip. The v4.35 palette is documented in CLAUDE.md §3 —
`--line` steps ~8% off `--paper` deliberately, so hairlines survive daylight at
arm's length; do not flatten that back.

**Suggested order:** §3a first — it is the highest value, and it resolves §1
and most of §7 as a side effect. Then §2, which is a copy and arithmetic fix
that stops the app being wrong at the worst possible moment. Then §5 and §6,
which are small. §3b when there is appetite for it; it is the one that turns
the log from a chore into the best feature in the app.
